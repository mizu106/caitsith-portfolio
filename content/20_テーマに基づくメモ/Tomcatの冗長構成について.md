## Tomcat 単体にロードバランサー機能はない

### Q1：Tomcatをインストールしたサーバー複数台のみで冗長クラスターを構成できますか。サーバー間の負荷の振り分けをTomcatで行う考え方です。
結論から言うと **Tomcat サーバー複数台だけでは、実運用レベルの冗長クラスター（負荷分散 + 障害時の自動切替）を構成するのは基本的に不可** です。  
Tomcat 単体にはロードバランサー機能がないためです。  
ただし、**セッションレプリケーションを使った “アプリケーションサーバークラスタ” は構築可能** です。

以下、詳しく解説します。

#### ✅ 1. Tomcat 単体にロードバランサー機能はない

Tomcat は **アプリケーションサーバー** であり、  
**ロードバランサー（LB）やプロキシ機能、ヘルスチェック機能は持ちません。**

そのため、以下の機能は Tomcat だけでは実現不可です：

| 必要な機能              | Tomcat 単体で可能？ |
| ------------------ | ------------- |
| 負荷分散 (ロードバランス)     | ❌ 不可          |
| ヘルスチェック            | ❌ 不可          |
| 障害検知・自動切替          | ❌ 不可          |
| Sticky session の制御 | ❌ 不可          |
| ルーティング制御           | ❌ 不可          |

実運用のクラスタはたいてい以下のいずれかをロードバランサーに使います：

- Apache HTTP Server + mod_jk / mod_proxy
- NGINX（最も一般的）
- HAProxy
- F5, A10 などハードウェアロードバランサー
- クラウド LB (ALB, ELB, Azure LB)
   
#### ✅ 2. Tomcat 同士だけでできること = **アプリケーションクラスタ**

Tomcat 自体は **セッションレプリケーション** を標準機能として持っています。

##### Tomcat のクラスタ機能：

- **DeltaManager**（全ノードにセッション複製）
- **BackupManager**（バックアップノードにだけ複製）
→ これにより **セッションの冗長化** は可能。
ただし、  
⚠ **トラフィックの振り分けは外部ロードバランサーが絶対に必要**
Tomcat のクラスタ機能はあくまで以下のみ：
**「複数 Tomcat 間でセッション状態を共有する」**

#### ❌ 3. 「Tomcat 同士で相互リクエスト転送して負荷分散」は現実的でない

もし次のような案を考えている場合：
> Tomcat A がリクエストを受けたら Tomcat B に転送して負荷を分散する
これは Tomcat の役割ではなく、機能もありません。  
HTTP reverse-proxy と LB が必要です。

Tomcat は内部に Web サーバーやリバースプロキシ機能を持たないため、  
**負荷分散の仕組みを自前で作るのは非現実的 & 不安定** です。

#### ✅ 4. どうしても Tomcat だけで “疑似ロードバランス” をしたい場合

一応、可能性として **Tomcat の組み込み Web サーバーではなく、アプリケーションコードで転送処理を書く** という手はあります。

例：
- Java の HttpClient で他ノードへ転送
- ラウンドロビン処理を自作

しかしこれは：
- 運用不能
- 障害検知不可
- レイテンシが悪化
- メンテ不能
- 保守不可
→ **絶対に非推奨** です。

#### ✅ 5. 正しい構成例（最小構成）

Tomcat だけで負荷分散は無理なので、最小構成はこうなります：

```
                 ┌──────────┐
                 │ NGINX / Apache │
                 └─────┬──────┘
                       │
        ┌─────────────┴─────────────┐
        │                             │
  ┌──────────┐                 ┌──────────┐
  │ Tomcat #1 │  <-- session --> │ Tomcat #2 │
  └──────────┘                 └──────────┘
```

- NGINX / Apache が負荷分散 & ヘルスチェック
- Tomcat はアプリを動かす
- クラスタリングは Tomcat の `server.xml` に設定  
    ※ 必要に応じてセッション複製

#### ⭐ 結論（Nobuyukiさん向けにわかりやすく）

##### **Tomcat だけでロードバランサーの代わりをして負荷分散＋冗長化することはできない。**
##### **Tomcat でできるのは “セッションクラスタリング” のみ。**
##### **実運用では必ず NGINX or Apache 等のロードバランサーが必要。**

必要なら以下の内容も作成します：
- NGINX + Tomcat の構成図
- Tomcat クラスタ設定例（server.xml）
- Sticky セッション（JSESSIONID）解説
- セッションレプリケーションの有無による構成比較
どれが必要ですか？


### Q2：Tomcatのセッションレプリケーションとはどのような機能でしょうか。
Tomcat の **セッションレプリケーション（Session Replication）** は、  
**複数台の Tomcat サーバー間でユーザーのセッション情報をリアルタイムに共有する仕組み** です。

これにより、以下が実現できます：
- **片方の Tomcat が落ちても、ユーザーはログインし直さずに処理を続けられる**
- ロードバランサーがどちらのノードに振り分けても、セッション状態が維持される

#### ✅ 1. セッションレプリケーションの役割
通常、セッションは **リクエストを受けた Tomcat のメモリだけに保存** されます。

```
Client → Tomcat #1 → JSESSIONID=abc123 （Tomcat #1 だけが保持）
```

この状態で Tomcat #1 が落ちると：
- セッションが消える
- ログイン情報やカート情報が消える  
    → **ユーザーはログインし直し**

これを防ぐために、
##### **セッションレプリケーションでは、Tomcat #1 のセッションを Tomcat #2 にコピーします。**

```
Client → Tomcat #1
         │
         └─ セッションデータを Tomcat #2 に複製
```

#### ✅ 2. どのような仕組みで複製している？

Tomcat は内部で **クラスタリング機能** を持っており、  
`server.xml` の `<Cluster>` 設定により、有効化できます。

主な方式：
##### ● **DeltaManager**
- すべてのノードにセッションをコピー
- 一貫性は強いが負荷が重い  
    （2台なら問題ないが増えると厳しい）
##### ● **BackupManager**
- プライマリ → バックアップ1台だけに複製
- よりスケーラブル

#### ✅ 3. 何が共有される？

セッションオブジェクト内の **Serializable なデータのみ**。
例：
- ログイン状態
- カート情報
- ユーザーの一時データ

##### ⚠ 注意：
Java オブジェクトが Serializable でないと複製できず、例外が発生します。

#### ✅ 4. 実際の動き

##### リクエスト 1：
1. LB → Tomcat #1 に振り分け
2. Tomcat #1 がセッションを生成
3. Tomcat #2 にセッションを複製

##### リクエスト 2：
- LB が Tomcat #2 に振り分けても  
    → **同じセッション状態で処理ができる**

##### Tomcat #1 がダウンした場合：
- Tomcat #2 はレプリケーション済みのセッションを使用
- ユーザーは継続して操作できる（ログイン維持）

#### ❌ 5. よく誤解される点

以下のものは Tomcat クラスタには含まれません：
- **負荷分散機能（LB）** ← 必ず外部が必要
- **ヘルスチェック機能**
- **フェイルオーバーの制御**（LB が担当）
Tomcat はあくまで「**セッションのコピー**」だけ担当します。

#### ✅ 6. 典型的な構成

```
                    ┌───────────┐
                    │  LoadBalancer│ (NGINX/Apache)
                    └───────┬─────┘
                            │
          ┌─────────────────┴─────────────────┐
          │                                     │
   ┌───────────┐                        ┌───────────┐
   │ Tomcat #1  │  ← セッション同期 →    │ Tomcat #2  │
   └───────────┘                        └───────────┘
```

#### ⭐ まとめ（シンプルに）

**Tomcat のセッションレプリケーションとは：**
> **複数 Tomcat 間でユーザーのセッション情報を共有して、  
> ノードが落ちてもユーザー操作を維持できるようにする機能。**

### Q3：ApacheとNGINXをロードバランサーにしてWebアプリケーションを構築する場合の例を教えて下さい。

以下では、**Apache** と **NGINX** をロードバランサー（リバースプロキシ）として利用し、  バックエンドに複数の **Tomcat** サーバーを置いた典型的な Web アプリケーション構成例を図とポイント込みでわかりやすく解説します。

#### 🚀 **1. Apache（httpd）を LB にした構成例**

##### 構成図
```
                       ┌────────────────────┐
                       │      Apache        │
                       │ (mod_proxy_balancer│
                       │   or mod_jk )      │
                       └─────────┬──────────┘
                                 │
                 ┌──────────────┴──────────────┐
                 │                               │
       ┌────────────────┐               ┌────────────────┐
       │   Tomcat #1    │               │   Tomcat #2    │
       └────────────────┘               └────────────────┘
```

##### ① 利用される主なモジュール

###### ● パターン A：**mod_proxy_balancer（HTTP/HTTPS）**
簡単・使いやすい、現在の主流。
- mod_proxy
- mod_proxy_http
- mod_proxy_balancer
- mod_lbmethod_byrequests（ラウンドロビン）

###### ● パターン B：**mod_jk（AJP プロトコル）**
- 昔ながらの Tomcat 連携方式
- AJP プロトコル
- 現在は非推奨寄り（セキュリティ事故もあり）
→ 2024年現在は **mod_proxy_http** を推奨。

##### ② Apache の設定例（mod_proxy_balancer）

###### **/etc/httpd/conf.d/balancer.conf**
```apache
<Proxy "balancer://mycluster">
    BalancerMember "http://10.0.1.11:8080"
    BalancerMember "http://10.0.1.12:8080"
    ProxySet lbmethod=byrequests
</Proxy>

<VirtualHost *:80>
    ProxyPass "/" "balancer://mycluster/"
    ProxyPassReverse "/" "balancer://mycluster/"
</VirtualHost>
```

###### 機能:
- **ラウンドロビンで Tomcat に振り分け**
- Tomcat が落ちても自動で検出（ファイルオーバー）
- HTTPS 終端（SSL Termination）も Apache 側で可能

##### ③ 運用でよく使われる構成

###### ● Apache を DMZ に置く
- クライアント → Apache（公開）
- 内部ネットワーク → Tomcat（非公開）

### ● 監視：mod_status
### ● WAF：mod_security（任意）

#### 🚀 **2. NGINX を LB にした構成例**

##### 構成図
```
                       ┌────────────────────┐
                       │       NGINX        │
                       │ (reverse proxy/LB) │
                       └─────────┬──────────┘
                                 │
                 ┌──────────────┴──────────────┐
                 │                               │
       ┌────────────────┐               ┌────────────────┐
       │   Tomcat #1    │               │   Tomcat #2    │
       └────────────────┘               └────────────────┘
```

##### ① NGINX が選ばれる理由
- 軽量
- 高速
- 負荷分散機能が強い（ヘルスチェック有効）
- 設定がシンプル
- SSL 終端が速い

##### ② NGINX の設定例

###### **/etc/nginx/conf.d/app.conf**
```nginx
upstream tomcat_backend {
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
}

server {
    listen 80;

    location / {
        proxy_pass http://tomcat_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

###### 機能:
- **ロードバランス（ラウンドロビン）**
- **障害ノードの切り離し**
- セッション維持（sticky module）対応
- SSL 終端
- キャッシュも可能（Apache より高速）

#### 🚀 **3. Apache vs NGINX の比較（Tomcat LB 構成）

| 項目        | Apache（mod_proxy） | NGINX          |
| --------- | ----------------- | -------------- |
| 処理速度      | 中                 | 高速（軽量）         |
| 設定の容易さ    | 普通                | 簡単             |
| Tomcat 連携 | mod_jk の歴史あり      | 最新構成向け         |
| SSL 終端    | できる               | かなり得意          |
| LB 機能     | 標準的               | 高機能・高速         |
| 静的ファイル配信  | 普通                | 超高速            |
| WAF       | mod_security 利用   | NGINX WAF（別製品） |

**→ 最近は NGINX を選ぶケースが圧倒的に多いです。**

#### 🚀 **4. 全体構成（冗長化込み）の実例図

##### ① シンプルな2台構成（LB + Tomcat）
```
Client
  ↓
┌───────────────┐
│ Apache/NGINX LB│
└───────┬────────┘
        │
 ┌──────┴──────┐
 │             │
Tomcat #1   Tomcat #2
```

##### ② 冗長ロードバランサー構成（実運用）
```
Client
   ↓
            ┌──────────────┐
            │   LVS / VRRP  │ ← LBの冗長化
            └──────┬───────┘
                   │
     ┌─────────────┴──────────────┐
     │                              │
┌───────────────┐           ┌───────────────┐
│  Apache LB #1  │           │  Apache LB #2  │
└───────┬────────┘           └────────┬──────┘
        │                               │
        └─────────────┬─────────────────┘
                      │
           ┌──────────┴─────────┐
           │                     │
    ┌──────────────┐    ┌──────────────┐
    │  Tomcat #1   │    │  Tomcat #2   │
    └──────────────┘    └──────────────┘
```

#### ⭐ まとめ

Apache / NGINX をロードバランサーにした Web アプリ構成は以下が共通：
- LB は「外向けの入口」
- Tomcat は「内部アプリケーションサーバ」
- LB がリクエストを振り分ける
- Tomcat 間でセッションレプリケーションを行えばフェイルオーバーも可能
現在のおすすめは **NGINX + Tomcat（HTTP）方式**。

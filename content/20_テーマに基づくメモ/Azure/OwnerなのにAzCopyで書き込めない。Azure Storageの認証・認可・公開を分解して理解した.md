# 何をしようとしているのか
Azure Storageの汎用v1（GPv1）ストレージアカウント廃止に伴い、ストレージアカウントの種類と操作方法を調べました。
調査の中で最も理解に時間がかかったのが`Shared Access Signature（SAS）`関係です。

この記事では、AzCopyによるBlob転送を実際に試しながら、Azure Storageの認証・認可構造を整理します。AzCopy自体の詳細な操作解説ではなく、「誰が、どの資格情報を使い、どの権限でBlobへアクセスしているのか」を中心に扱います。

# AzCopyを使用したファイル転送

## Azure Storageの認可方式
Azure Storageのデータへのアクセスを認可する主な方式として、Microsoft Entra ID、Shared Access Signature（SAS）、Shared Keyがあります。この記事では、この3方式を中心に扱います。

端的に言うと、Microsoft Entra IDでプリンシパルを認証し、RBACで認可する方法と、SASという署名（文字列）を要求に付加して認可する方法があると考えて下さい。

プリンシパルで認証して、そのRBACで権限を決める場合、ストレージアカウントは管理プレーンとデータプレーンという２層に分かれて権限を設定する必要があります。単なる所有者や共同作成者のロールは管理プレーンの操作権限を、Storage Blob データ共同作成者はデータプレーンの操作権限を持ちます。

要するにAzCopyでBlobにアクセスする場合、所有者や共同作成者のロールがついていても、Storage Blob データ共同作成者などのデータプレーンのロールが付いていなければ、ファイルの読み書きはできないということです。

| 方式                 | 資格情報・署名の種類                          | 概要                                                                                               |
| ------------------ | ----------------------------------- | ------------------------------------------------------------------------------------------------ |
| Microsoft Entra ID | ユーザープリンシパル<br>サービスプリンシパル<br>マネージドID | プリンシパルにRBACを設定してEntra IDで<br>認証する事で操作権限を決定します。                                                   |
| SAS                | サービスSAS<br>アカウントSAS                 | 条件を指定してSASという署名を作成し、<br>そのSASを要求に付加して認可します。<br>操作権限はSASを作成する時に指定します。                             |
| SAS                | ユーザー委任SAS                           | SAS作成時にサインインしていたユーザーの情報が<br>埋め込まれ、SAS作成元ユーザーのRBACと<br>SASトークン内の`sp`の組み合わせで権限が決まります。              |
| 共有キー               | ストレージアカウントキー                        | PortalやAPIからのBlob操作で使用される場合があります。<br>サービスSASとアカウントSASの署名にも使われます。<br>AzCopyでは使用しない為、本記事では深入りしません。 |
※ユーザー委任SASに埋め込まれる情報は、正しくはプリンシパル（ユーザープリンシパル、サービスプリンシパル、マネージドID）になります。本記事ではコマンドでのSAS作成を扱っていないため分かりやすくユーザーとしました。

## SASを使用してみる
SASには、サービスSAS、アカウントSAS、ユーザー委任SASの3種類があります。  この記事では、Microsoft Entra IDやRBACとの関係が最も分かりにくいユーザー委任SASを中心に扱います。  
ユーザー委任SASを理解すると、ストレージアカウントキーで署名するサービスSASやアカウントSASとの違いも見えやすくなります。

SASとは操作する宛先のストレージアカウントとコンテナをURLで示して、その後ろにSASトークンを書いて送ることで、ストレージへのアクセスを認可する方式です。
SASトークンには`sp=`（許可された操作）、`se=`（有効期限）、`sr=`（リソース種別）などの平文パラメータと、それらすべてを署名した`sig=`（署名）が含まれます。

そして、サービスSASとアカウントSASはストレージアカウントキーで署名します。（ストレージアカウントのメニューで、セキュリティとネットワーク>アクセスキーで表示されるやつ）
一方、ユーザー委任SASは、ユーザー委任キー（Entra IDから発行される一時鍵）を使用して署名します。

基本はAzCopyを使用した時に認可されてspに書かれた権限により何ができるかが決まりますが、ユーザー委任SASはspによる権限とSASを作成したプリンシパルに付与されているRBACの二段階で認可が行われます。
spで作成、書き込み、削除などの強い権限を与えていても、SASを作成したプリンシパルにストレージアカウントのデータプレーンにアクセスする権限がなければ何もできません。

### SAS URLを組み立てる
以下のようにストレージアカウント名、コンテナ名、SASを変数に組み込んでアクセスします。以下の例ではローカルの`"C:\AzCopyLab\hello.txt"`からストレージアカウントにファイルをコピーする例です。
``` PowerShell
# SAS URLの組み立て
$accountName = < ストレージアカウント名 >
$containerName = < コンテナ名 >
$sas = < 作成したSAS文字列 >
$containerUrl = "https://$accountName.blob.core.windows.net/$containerName"

azcopy copy "C:\AzCopyLab\hello.txt" "$containerUrl/hello-sas.txt?$sas"
```

## マネージドIDを使用してみる
ではここでもう一つの分かりにくい認証方法であるマネージドIDを見ていきましょう。ユーザープリンシパルとサービスプリンシパルは明示的なサインインが発生する以外は、マネージドIDでのAzCopyとほぼ同じ操作になるので省略します。

マネージドIDは、VMなどのAzureリソースにMicrosoft Entra ID上のプリンシパルを割り当てる仕組みです。 VM上で実行したアプリケーションやAzCopyは、そのマネージドIDに割り当てたプリンシパルを使って自動的にMicrosoft Entra IDのトークンを取得し、RBACに基づいてBlobへアクセスします。
このプリンシパルへのサインインはAzureが管理するため、ユーザープリンシパルやサービスプリンシパルのような明示的なサインインは不要です。（明示的にサインインすることもできます）

### VMのマネージドIDを有効化する
対象のVMなどのリソースを選択してメニューから`セキュリティ>ID`を選択、`システム割り当て済`を選択して状態をオンにします。（必ず保存ボタンを押して下さい）
これでリソースに割り当てたプリンシパルが作成され紐づけされます。
![[Pasted image 20260816022922.png]]
### ストレージアカウントにデータプレーン用RBACを割り当てる
VMのマネージドIDを有効化したらストレージアカウントのアクセス権を割り当てます。対象のストレージアカウントを開き`アクセス制御（IAM）`を選択します。メニューから`追加>ロール割り当ての追加`を選択します。
![[Pasted image 20260816023409.png]]
ロールの割り当ては検索窓に`Storage Blob`と入力して必要なRBACを割り当てます。この時ストレージアカウントのデータプレーンに対する権限を持つRBACを選択するのがポイントになります。（単なる所有者や共同作成者ロールは管理プレーンへの権限になります）
![[Pasted image 20260816023512.png]]
メンバーにはマネージドIDを選択して、権限を与えたいVMを選択します。
![[Pasted image 20260816024010.png]]
レビューと割り当てを実行します。
![[Pasted image 20260816024219.png]]
これで指定したVMのマネージドIDにストレージアカウントにアクセスできるロールが付与されるので、VM上で実行したAzCopyはストレージアカウントにアクセスできるようになります。

### VM上のAzCopyから転送する
それではVM上でAzCopyしてみましょう。見ての通りSASを使用せずにストレージアカウントの操作ができています。
``` PowerShell
# AzCopyにManaged Identityで自動ログインさせる
$Env:AZCOPY_AUTO_LOGIN_TYPE = "MSI"

# コンテナURLの設定
$accountName = "teststorage01stc01"
$containerName = "azcopy-lab"
$containerUrl = "https://$accountName.blob.core.windows.net/$containerName"

# アップロード
azcopy copy "C:\AzCopyLab\hello-sas.txt" "$containerUrl/hello-sas.txt"

# ダウンロード
azcopy copy "$containerUrl/hello-sas.txt" "C:\AzCopyLab\hello-from-storage.txt"

# 一覧表示
azcopy list $containerUrl
```


## 対話式のサインインが不要になる
ユーザープリンシパルやサービスプリンシパルを使用する場合も、SASなしのAzCopyコマンド自体は似た形になります。 ただし、AzCopyがどの資格情報を使うかは `AZCOPY_AUTO_LOGIN_TYPE` の指定に従います。

# 背景にある仕組み

## 管理プレーンとデータプレーン
Azure Storageの権限を考える時に分かりにくいのが、同じストレージアカウントに対する操作でも、**管理プレーン**と**データプレーン**で必要な権限が分かれていることです。

| プレーン    | 説明                                                                                                                                     |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 管理プレーン  | ストレージアカウントというAzureリソースそのものを管理するための操作です。<br>たとえば、ストレージアカウントの作成、設定変更、ネットワーク設定、<br>アクセスキーの表示、診断設定の変更などが該当します。                             |
| データプレーン | Blob、File、Queue、Tableといったストレージサービス内のデータそのものを<br>読み書きする操作です。Blobであれば、コンテナ内のファイルを一覧表示する、<br>アップロードする、ダウンロードする、削除する、といった操作がデータプレーンに当たります。 |
この違いが重要になるのは、Azure RBACのロールもこの2つの層で分かれているためです。
例としてどのプレーンにどのロールが権限を持つのか、下表にまとめました。

| 権限があるプレーン | ロール                                                           | 実行可能操作              |
| --------- | ------------------------------------------------------------- | ------------------- |
| 管理プレーン    | `所有者`<br>`共同作成者`                                              | ストレージアカウントの設定を変更できる |
| データプレーン   | `Storage Blob Data Reader`<br>`Storage Blob Data Contributor` | Blobの中身を読み書きできる     |
実際、ストレージアカウントの画面をAzure Portalで開ける、設定を確認できる、IAMを見られる、という状態でも、Blobの中身をAzCopyで操作できるとは限りません。AzCopyでBlobを読み書きする場合は、要求がBlobサービスに対するデータ操作になるため、データプレーン側の認可が必要になります。

## SAS、SASトークン、SAS URLの違い
実際の操作ではまとめて「SAS」と呼ばれることが多いですが、仕組みを理解するには分けて考えた方が分かりやすくなります。

| 用語                           | 説明                                                                                                                                                                          |     |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- |
| SAS(Shared Access Signature) | 日本語では **共有アクセス署名**。これは、Azure Storageのリソースに対して、期間や操作権限を限定したアクセスを許可する仕組み全体を指します。Microsoft Learnでも、SASはストレージアカウント内のリソースに対して、アクセス対象、許可される操作、有効期間などを細かく制御してアクセスを委任する仕組みだとされています。 |     |
| SASトークン                      | URLの `?` 以降に付くクエリ文字列の部分です。この中には、許可する操作、有効期限、対象リソース、署名などが含まれています。<br>（例）<br>?sv=2024-11-04&st=2026-08-16T00:00:00Z&se=2026-08-16T01:00:00Z&sp=rw&sr=c&sig=xxxxxxxx           |     |
| SAS URL<br>SAS URI           | アクセス対象のURLとSASトークンを結合した完全なURLです。<br>（例）<br>https://<storage-account>.blob.core.windows.net/<container>/<blob-name>?sv=...&sp=...&se=...&sr=...&sig=...                      |     |
| 共有アクセストークン                   | Azure Portalの日本語UIなどで見かける表記。この記事ではSASトークン相当として扱います。                                                                                                                         |     |
| 共有アクセス署名                     | Shared Access Signatureの正式な日本語訳です。                                                                                                                                          |     |

## SASトークンの構造
SASトークンは、URLの `?` 以降に付くクエリパラメーターの集まりです。  
見た目は単なる文字列ですが、中には「どのバージョンの仕様で」「いつからいつまで」「どの操作を」「どのリソースに対して」許可するのか、そしてそれらの条件を改ざんされていないことを確認するための署名が含まれています。

たとえば、以下のような文字列がSASトークンです。
```
sv=2024-11-04&st=2026-08-16T00:00:00Z&se=2026-08-16T01:00:00Z&sp=rw&sr=c&spr=https&sig=xxxxxxxx
```

この文字列は、ざっくり分けると以下のような構造になっています。

| パラメーター | 意味          | 変化する主な理由             |
| ------ | ----------- | -------------------- |
| `sv`   | SASの仕様バージョン |                      |
| `st`   | 開始時刻        | 生成時刻や指定値が変わる         |
| `se`   | 有効期限        | 生成時刻や指定期限が変わる        |
| `sp`   | 許可操作        | Read、Writeなどの選択が変わる  |
| `sr`   | 対象リソース      | Blob、コンテナなどの対象が変わる   |
| `sip`  | 許可IP        | IP制限を変える             |
| `spr`  | 許可プロトコル     | HTTPSのみ、HTTPSとHTTPなど |
| `sig`  | 署名          | 署名対象のパラメーターや署名キーが変わる |
このうち、人間が読み取れる条件は `st`、`se`、`sp`、`sr`、`spr` などです。  
たとえば `sp=rw` であれば、読み取りと書き込みが許可されていることが分かります。`se` を見れば、そのSASがいつ失効するかも分かります。

一方で、最も重要なのが `sig` です。  
`sig` は、SASトークン内の条件から作られた署名です。Azure Storageはリクエストを受け取った時に、この署名を検証します。もし `sp` や `se` を後から手で書き換えても、署名と内容が一致しなくなるため、そのSASは無効になります。

SASトークンは、Azure Storage側に「発行済みトークン」として保存されているものではありません。  
リクエスト時に、SASトークンに含まれる条件と署名をAzure Storageが検証し、有効期限内であり、署名が正しく、要求された操作が `sp` の範囲内であればアクセスが許可されます。SASは、アクセス対象、許可操作、有効期間などを指定してAzure Storageリソースへの限定アクセスを許可する仕組みです。

サービスSASやアカウントSASでは、この署名はストレージアカウントキーを使って作成されます。  
一方、ユーザー委任SASでは、Microsoft Entra IDの資格情報を使って取得したユーザー委任キーで署名されます。ユーザー委任SASを作成するには、まずユーザー委任キーを要求し、そのキーでSASを署名します。これは、サービスSASやアカウントSASでストレージアカウントキーを使って署名するのに相当する仕組みです。

また、ユーザー委任SASでは `sk...` で始まるパラメーターが含まれることがあります。  
たとえば、`skoid`、`skt`、`ske`、`sks`、`skv` などです。これらは、ユーザー委任キーに関する情報を表します。

代表的には以下のような意味になります。

| パラメーター  | 意味                           |
| ------- | ---------------------------- |
| `skoid` | ユーザー委任キーを要求したプリンシパルのオブジェクトID |
| `skt`   | ユーザー委任キーの有効開始時刻              |
| `ske`   | ユーザー委任キーの有効期限                |
| `sks`   | 対象サービス                       |
| `skv`   | ユーザー委任キーのサービスバージョン           |

SASトークンは、`sp` や `se` などの読み取れる条件と、それらを改ざんされていないことを確認する `sig` で構成される、期限付き・権限付きのアクセス許可情報です。

### SASを再生成すると文字列は変わるか
**通常は作成する都度変化します**。ただし、Blob本体のURL部分は同じで、主に後ろへ付く**SASトークン部分**が変わります。

（例）URLの構造
``` text
# Blob URL  
https://<account>.blob.core.windows.net/<container>/<blob>  

# SASトークン  
sv=...&st=...&se=...&sp=...&sr=...&sig=...  

# Blob SAS URL  
https://<account>.blob.core.windows.net/<container>/<blob>?sv=...&sig=...
```
SASトークンには、対象リソース、アクセス許可、有効期間、署名などが含まれます。

では、同一条件で再作成した場合はどうでしょうか。
厳密には、**SASの種類と生成方法によります**。

サービスSASやアカウントSASで、次の条件がすべて完全に同一なら、同じ署名文字列が生成される可能性があります。署名は、SASの署名対象フィールドから構成した文字列へHMAC-SHA256を適用して生成されるためです。
- 同じストレージアカウントキー
- 同じ対象リソース
- 同じ開始時刻
- 同じ有効期限
- 同じアクセス許可
- 同じサービスバージョン
- 同じIP・プロトコル制限
- 同じ応答ヘッダー指定
- 同じパラメーター構成

一方、今回の**ユーザー委任SAS**では、ユーザー委任キーに関する情報もトークンへ入ります。Microsoft Entra資格情報を基に取得したユーザー委任キーで署名されるため、再生成時には同じ権限指定でもトークン全体が変化しやすいと考えるのが安全です。

### SASを再生成すると古いSASは失効するか
基本的に、同じ条件でSASを再生成しても、古いSASが自動的に失効するわけではありません。  SASはサーバー側に「発行済みトークン一覧」として保存されているものではなく、署名付きのクエリ文字列です。  そのため、有効期限内で署名が正しければ利用できます。

### 古いSASを無効化する方法
古いSASを無効化する主な方法は以下です。  

- 有効期限が切れるのを待つ  
- 署名に使ったストレージアカウントキーをローテーションする  
- 保存済みアクセスポリシーを使っているサービスSASなら、ポリシーを変更または削除する  
- ユーザー委任SASなら、ユーザー委任キーの有効期限を短く設計する

### AzurePortalからBlobを操作する時に起きていること
Azure PortalでBlobを操作する場合も、裏側ではBlobデータへのアクセス認可が必要です。  Portalにサインインできることと、Blobの中身を読み書きできることは同じではありません。  

ストレージアカウントの設定を見るだけなら管理プレーンの権限で足りますが、Blobの中身をMicrosoft Entra ID資格情報で操作するには、Storage Blob Data ReaderやStorage Blob Data Contributorなどのデータプレーンロールが必要です。

また、Azure Portalでは、権限がある場合にストレージアカウントキーを使ってBlobデータへアクセスすることもあります。

# BLOBを匿名アクセス許可で公開して直接表示する
ここまで、SASやマネージドIDを使ってBlobへアクセスする方法を見てきました。  
一方で、画像やHTMLファイル、PDFなどを「URLを知っている人がそのまま開ける」状態にしたい場合は、Blobの匿名読み取りアクセスを使う方法があります。

この方式では、静的Webサイト機能の `$web` コンテナやWebサイト用エンドポイントは使いません。  
通常のBlob URLをそのまま公開URLとして使います。

この機能は、Azure Storageでは主に「匿名読み取りアクセス」または「Blob匿名アクセス」と呼ばれます。 英語では anonymous read access for containers and blobs です。
Azure Storageでは、コンテナとBlobに対して匿名読み取りアクセスを構成でき、既定では匿名アクセスは許可されません。ストレージアカウント側の許可とコンテナ側のアクセスレベル設定の両方が関係します。

## 必要な設定
Blobを匿名で直接表示するには、次の2つの設定が必要です。
1. ストレージアカウント側で Blob匿名アクセスを許可する  
2. 対象コンテナ側で 匿名アクセスレベル を Blob または コンテナ に変更する

Azure Storageの匿名アクセスは、ストレージアカウント側の設定とコンテナ側の設定の2段階で制御されます。ストレージアカウント側で匿名アクセスを許可しても、コンテナ側がプライベートのままだとBlobデータは匿名では読めません。

## ストレージアカウント側の設定
ストレージアカウント側への匿名アクセスを許可します。ストレージアカウントのメニューから`設定>構成`で表示された画面で`Blob匿名アクセスを許可する`を有効化します。
![[Pasted image 20260816084544.png]]

## コンテナ側の設定
コンテナ側への匿名アクセスを許可します。対象のコンテナを選択して上部のメニューから`アクセスレベルの変更>Blob`を選択します。
![[Pasted image 20260816090020.png]]
![[Pasted image 20260816090059.png]]
ここで選べる設定は以下です。

| アクセスレベル | 匿名でBlobを読めるか | 匿名で一覧表示できるか | 用途                               |
| ------- | ------------ | ----------- | -------------------------------- |
| プライベート  | ❌️           | ❌️          | 既定値。認可されたユーザーだけがアクセスする           |
| Blob    | ⭕️           | ❌️          | ファイルURLを知っている人だけに直接表示させたい場合      |
| コンテナ    | ⭕️           | ⭕️          | Blobの直接表示に加えて、コンテナ内の一覧取得も許可したい場合 |

対象のBlobを選択したときに現れるURLをブラウザーに入力します。

## コンテナ内の一覧を匿名アクセスして表示する
アクセスレベルでコンテナを選択すると、匿名ユーザーでもコンテナ内のBlobの一覧を見ることができます。以下にコンテナを選択した場合のコンテナ内の一覧表示方法を記載しますが、URLの指定方法が変わるのとXML表示のためあまり扱いやすくありません。

コンテナ内の一覧を取得したい場合は、次のようにBlob Storageの一覧取得用クエリを付けます。
```
https://<storage-account>.blob.core.windows.net/<container>?restype=container&comp=list
```

## セキュリティ上の注意
匿名アクセスを許可すると、そのURLを知っている人は認証なしでBlobを読み取れます。  
特にコンテナのアクセスレベルを `コンテナ` にすると、Blobの読み取りだけでなく、コンテナ内の一覧取得も匿名で可能になります。

これまで扱ってきたようなEntra IDでの認証やSASでの認可を行わずに、コンテナ単位でアクセスを許可する設定となるため、十分注意して使用する必要があります。

# まとめ
まとめると、Azure StorageのBlobアクセスは、単に「URLがあるから読める」「所有者だから書ける」と考えると混乱します。  

Blobへのアクセスでは、次の観点を分けて考える必要があります。  
- Microsoft Entra IDとRBACで認可するのか  
- SASで限定的なアクセス権を渡すのか  
- Blobを匿名読み取りで公開するのか  
- 管理プレーンの操作なのか、データプレーンの操作なのか  

特に、所有者や共同作成者のロールがあっても、Blobデータの読み書きには`ストレージ BLOB データ共同作成者`などのデータプレーンロールが必要になる点は重要です。  

SAS、マネージドID、匿名読み取りアクセスはどれもBlobへアクセスする方法ですが、権限の持たせ方が異なります。  この違いを理解しておくと、AzCopyのエラーやPortalでの表示、Blob URLの公開設定をかなり整理しやすくなります。
